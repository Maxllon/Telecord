# Telecord — Инструменты проекта

## 1. Язык программирования: Rust

**Выбран:** Rust (edition 2021).

**Почему:**

- **Безопасность.** Telecord проксирует переписку между организациями и хранит токены ботов. Memory safety и строгая типизация снижают риск утечек и падений.
- **Асинхронность.** Система обслуживает много одновременных соединений с разными API. `tokio` + `async/await` дают зрелую модель конкурентности.
- **Трейты.** Адаптеры мессенджеров удобно описываются через трейты: ядро не знает деталей API, адаптер реализует общий интерфейс.
- **Единый бинарник.** `bridge` и `cli` собираются как обычные Rust-бинарники, деплой на VPS тривиален.
- **Экосистема.** Есть зрелые крейты для Telegram (`teloxide`) и Discord (`serenity`).

**Альтернативы и почему не выбраны:**

- **Go.** Проще в разработке, но менее строгая типизация и слабее система трейтов (интерфейсы проще, но нет generics-абстракций уровня Rust).
- **Node.js / TypeScript.** Быстрее в разработке адаптеров, но слабее в долгоживущих процессах, хуже с безопасностью, тяжелее по памяти.
- **Python.** Удобен для прототипов, но плохо подходит для долгоживущего сервиса под нагрузкой.

> Rust выбран осознанно, с пониманием, что разработка будет медленнее, чем на Go/Node.

## 2. Основные крейты

### 2.1. Runtime и асинхронность

| Крейт | Назначение | Почему |
| --- | --- | --- |
| tokio | Async runtime | Де-факто стандарт в Rust |
| async-trait | Async-методы в трейтах | Позволяет `MessengerAdapter` быть async |
| tokio-util | CancellationToken | Graceful shutdown |
| futures | Утилиты для стримов и комбинаторов | Стандарт |

### 2.2. Сериализация и данные

| Крейт | Назначение | Почему |
| --- | --- | --- |
| serde | Сериализация/десериализация | Стандарт |
| serde_json | JSON | API мессенджеров |
| uuid | Идентификаторы | Логические ID |
| chrono | Время | Timestamps |

### 2.3. Сеть

| Крейт | Назначение | Почему |
| --- | --- | --- |
| reqwest | HTTP-клиент | Стандарт |
| axum | HTTP-сервер для bridge | Лёгкий, tokio-native |
| hyper | Нижележащий HTTP | Через axum, напрямую не используем |
| tower | Middleware | Вместе с axum |

### 2.4. База данных

| Крейт | Назначение | Почему |
| --- | --- | --- |
| sqlx | Async SQL + миграции | Compile-time проверка запросов |
| postgres | Драйвер | Через sqlx |

**СУБД:** PostgreSQL.

**Почему Postgres:**

- JSONB для вложений и гибких полей.
- UUID из коробки.
- Надёжность и предсказуемость.
- Легко поднять в Docker рядом с bridge.

### 2.5. CLI и конфигурация

| Крейт | Назначение | Почему |
| --- | --- | --- |
| clap | Парсинг аргументов CLI | Стандарт |
| toml | Конфиг-файлы | Читаемо, привычно |
| envy или figment | Override через env | Секреты не в файле |

### 2.6. Логирование и ошибки

| Крейт | Назначение | Почему |
| --- | --- | --- |
| tracing | Структурные логи | Асинхронный контекст |
| tracing-subscriber | Подписчик для логов | Стандарт |
| thiserror | Ошибки в библиотеках | Явные типы ошибок |
| anyhow | Ошибки в бинарниках | Удобство |

> **Правило:** `println!` в коде не используется. Только `tracing`.

### 2.7. Утилиты

| Крейт | Назначение |
| --- | --- |
| governor | Rate-limit |
| backoff или ручная реализация | Экспоненциальный backoff |
| dotenvy | Загрузка `.env` при разработке |

## 3. Адаптеры мессенджеров

| Мессенджер | Крейт | Статус |
| --- | --- | --- |
| Telegram | teloxide | Планируется в MVP |
| Discord | serenity | Планируется после MVP |
| VK | vk-rs или собственный HTTP-клиент | Позже |
| Max | Собственный HTTP-клиент | Позже |

> **Правило:** адаптер — отдельный crate в `clients/`. Специфика мессенджера не протекает в `core` и `bridge`.

| Инструмент | Назначение |

| Cargo workspace | Монорепозиторий |

| Docker | Деплой bridge + Postgres на VPS |
| GitHub Actions (или аналог) | CI: fmt + clippy + test |

## 6. Что не используется и почему

| Технология | Почему нет |
| --- | --- |
| ORM (Diesel, SeaORM) | sqlx даёт достаточно, без магии |
| gRPC между адаптерами | Один процесс, IPC не нужен |
| Redis | Не нужен на MVP; добавить при необходимости |
| Микросервисы | Избыточно; один бинарник bridge |
| Web-фреймворк с SSR | Нет веб-UI в MVP |

## 7. Принципы выбора зависимостей

- **Минимум зависимостей.** Каждый новый крейт — обоснование.
- **Активная поддержка.** Крейт должен обновляться.
- **Понятная лицензия.** MIT/Apache-2.0.
- **Без «магии».** Предпочтение явным API (sqlx > Diesel).
- **Async-first.** Все сетевые крейты — tokio-native.
