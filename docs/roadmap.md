# Telecord — План разработки

## Фаза 1. MVP: Telegram ↔ Telegram

**Цель:** доказать, что мост работает. Два Telegram-чата, связанные в один виртуальный чат, обмениваются сообщениями в обе стороны.

**Объём:**

- Workspace, core с доменными типами и трейтом `MessengerAdapter`.
- Мок-адаптер для тестов роутера.
- Роутер: дедупликация, loop protection, рассылка.
- Адаптер Telegram (`teloxide`).
- PostgreSQL + миграции.
- CLI: регистрация виртуального чата, привязка физических чатов, список чатов.
- Graceful shutdown, supervisor для адаптеров.

**Критерий готовности:**

- Сообщение, отправленное в чат A, появляется в чате B, и наоборот.
- Повторная доставка апдейта не создаёт дубликат.
- Сообщение не уходит в бесконечный цикл.
- Убийство и перезапуск bridge не ломает состояние.

## Фаза 2. Ближайшее развитие: + Discord

**Цель:** подтвердить, что архитектура расширяется без изменения ядра.

**Объём:**

- Адаптер Discord (`serenity`).
- Capabilities адаптеров: где edit/delete не поддерживаются — fallback-стратегия.
- Edit и Delete end-to-end.
- Rate-limit и backpressure.
- Виртуальные пользователи в базовом виде: `id` + `display_name`, отображение в чужих мессенджерах.
- HTTP API для CLI.

**Критерий готовности:**

- Telegram ↔ Discord работает в обе стороны.
- Edit в Telegram отражается в Discord (с учётом возможностей).
- Delete в Discord отражается в Telegram.
- Виртуальный пользователь отображается осмысленно в обоих мессенджерах.
- Rate-limit мессенджера не роняет bridge.

## Фаза 3. Расширение: + VK + Max

**Цель:** довести число поддерживаемых мессенджеров до четырёх.

**Объём:**

- Адаптер VK.
- Адаптер Max.
- Обработка специфики каждого мессенджера (форматы вложений, ограничения на длину, reply).
- Метрики (prometheus) и health-checks.
- Пилот на реальной аудитории (кафедра / школа).

**Критерий готовности:**

- Все четыре мессенджера работают в одном виртуальном чате.
- Мониторинг показывает состояние адаптеров.
- Есть документация для администратора.
- Пилот прошёл без критичных сбоев.
